# Lesson: Secrets Management — Never Put Keys in Code

## [WHEN] You need this when:
1. Your pipeline needs API keys, database passwords, or SSH keys.
2. Someone accidentally committed a secret to Git.
3. You need different credentials for staging vs production.
4. An audit asks "how do you manage secrets?"

## [INTENT] "Handle credentials safely throughout the CI/CD pipeline."

## [CONTEXT]
Secrets (API keys, passwords, tokens) are the number one security
risk in CI/CD. Exposed secrets lead to data breaches, unauthorized
access, and very bad days. The rule is simple: NEVER in code. EVER.

## [ACTION] Secrets in CI/CD

### GitHub Actions secrets:
  # Set in: Settings → Secrets and variables → Actions
  # Use in workflow:
  steps:
    - name: Deploy
      run: ./deploy.sh
      env:
        API_KEY: ${{ secrets.API_KEY }}
        DB_PASSWORD: ${{ secrets.DB_PASSWORD }}

  # Secrets are:
  # - Encrypted at rest
  # - Masked in logs (replaced with ***)
  # - Not available in forked repos (security)
  # - Scoped to repo or organization

### Environment-specific secrets:
  # Settings → Environments → staging → secrets
  # Settings → Environments → production → secrets

  deploy-staging:
    environment: staging
    steps:
      - run: echo "DB=${{ secrets.DATABASE_URL }}"
        # Uses STAGING database URL

  deploy-production:
    environment: production
    steps:
      - run: echo "DB=${{ secrets.DATABASE_URL }}"
        # Uses PRODUCTION database URL (different secret, same name)

### Docker secrets (build-time vs runtime):
  # WRONG — secret baked into image:
  ENV API_KEY=sk-12345                    # ← visible in image layers!

  # RIGHT — passed at runtime:
  docker run -e API_KEY=$API_KEY myapp    # ← not in image

  # RIGHT — Docker secrets (Swarm/Compose):
  secrets:
    db_password:
      file: ./secrets/db_password.txt
  services:
    app:
      secrets:
        - db_password

### What to do when a secret is leaked:
  1. REVOKE the secret IMMEDIATELY (regenerate API key, rotate password)
  2. Check access logs for unauthorized use
  3. Remove from Git history:
     git filter-branch or BFG Repo-Cleaner
  4. Force push to rewrite history
  5. Notify affected parties
  6. Add pre-commit hooks to prevent future leaks

### Pre-commit secret scanning:
  # .pre-commit-config.yaml
  repos:
    - repo: https://github.com/Yelp/detect-secrets
      rev: v1.4.0
      hooks:
        - id: detect-secrets
          args: ['--baseline', '.secrets.baseline']

### GitHub secret scanning:
  GitHub automatically scans pushes for known secret patterns
  (AWS keys, GitHub tokens, Stripe keys, etc.) and alerts you.
  Enable: Settings → Code security and analysis → Secret scanning

### OIDC (passwordless CI/CD):
  # Instead of storing AWS credentials as secrets:
  permissions:
    id-token: write

  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789:role/github-actions
      aws-region: us-east-1

  # No secrets stored! GitHub generates a temporary token.
  # AWS trusts GitHub's identity provider.

## [EXPECTED RESULT]
Your pipeline has zero hardcoded secrets. Credentials are encrypted,
environment-scoped, and rotatable without changing code.

## Technician Tip:
Audit your secrets quarterly:
  1. List all secrets in GitHub Settings
  2. For each: is it still needed? When was it last rotated?
  3. Remove unused secrets
  4. Rotate credentials that are >90 days old

## Common Pain Point:
"Secret is empty in the workflow" → check the secret NAME.
Secrets are case-sensitive. API_KEY != api_key != Api_Key.
Also: secrets are not available in forked repo PRs (by design).
