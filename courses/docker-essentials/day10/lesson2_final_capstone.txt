# Final Capstone: The Migration Crisis

## THIS IS NOT A HOMEWORK ASSIGNMENT.

This is a simulated professional engagement. You are the DevOps
engineer. There's no step-by-step guide. You own the outcome.

────────────────────────────────────────────────────

## PHASE 1 — Problem Context

### The Scenario:

HealthTrack is a 15-person health tech startup running a patient
appointment scheduling system. Currently everything runs on a
single bare-metal server:

  - Node.js API (Express)
  - PostgreSQL 14 database (4 years of patient data)
  - Redis cache
  - Nginx reverse proxy

Last week the server's disk controller showed SMART warnings.
The CTO says: "We have maybe 2 months before that disk fails.
Containerize everything so we can deploy anywhere."

Also: HIPAA compliance requires that patient data never leaves
encrypted storage, secrets aren't in source code, and there's
an audit trail for deployments.

### What you know:
  - The app listens on port 3000
  - PostgreSQL has 12GB of patient data
  - Redis is used for session storage
  - The team currently deploys with ssh + git pull + pm2 restart
  - There are integration tests (npm test) that hit the real database
  - The app reads DB credentials from environment variables

### What you DON'T know (you must decide):
  - Base images for each service
  - Network topology (which services need to talk to which)
  - Volume strategy for the database
  - How to handle secrets (env vars? Docker secrets? Vault?)
  - Whether to use compose or Swarm or both
  - How to handle the database migration from bare-metal to container

## PHASE 4 — Execution

Build the containerized stack:

### 4A. Dockerfiles
  - app/Dockerfile — Node.js app with:
    - Multi-stage build (build → production)
    - Non-root user
    - Health check on /health
    - .dockerignore (node_modules, .git, .env, tests)

  - nginx/Dockerfile (or nginx.conf) — reverse proxy config

### 4B. Docker Compose (docker-compose.yml)
  - 4 services: app, db, cache, proxy
  - Named volumes for database persistence
  - Custom networks (frontend for proxy+app, backend for app+db+cache)
  - Backend network marked internal (db/cache can't reach internet)
  - Health checks on all services
  - Resource limits
  - Environment variables for configuration
  - depends_on with health conditions

### 4C. Security Hardening
  - No secrets in Dockerfile or compose file
  - .env file for local development (gitignored)
  - Document how secrets would be managed in production
  - Non-root users in all containers
  - Read-only filesystem where possible

### 4D. Operational Scripts
  - scripts/backup-db.sh — dumps PostgreSQL to a file with timestamp
  - scripts/restore-db.sh — restores from a dump file
  - scripts/health-check.sh — verifies all services are healthy

## PHASE 5 — Failure Injection

⚠️ SOMETHING GOES WRONG.

After building the stack, simulate ONE:

  A) The database container restarts and patient data is gone.
     You discover the volume wasn't configured correctly — data was
     written to the container's writable layer, not the volume.
     Diagnose, fix, verify persistence, and document.

  B) The app container runs but can't connect to the database.
     Logs show "Connection refused to db:5432" — but the db
     container is running. Investigate network configuration,
     service readiness, and DNS resolution.

  C) A developer accidentally pushes a docker-compose.yml that
     contains the production database password in plain text.
     It's in the Git history. Handle the incident: rotate the
     credential, purge from history, prevent recurrence.

Pick ONE. In INCIDENT.md document:
  1. What happened (timeline)
  2. Root cause
  3. Immediate fix
  4. Permanent prevention
  5. HIPAA implications (if any)
