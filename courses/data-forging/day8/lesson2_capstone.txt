# Final Capstone: The Data Investigation

## THIS IS NOT A HOMEWORK ASSIGNMENT.

You are a contract data analyst. A client hired you to
make sense of their data. Your deliverable is the pipeline
AND the answers.

────────────────────────────────────────────────────

## PHASE 1 — Problem Context

### The Scenario:

FreshBites is a meal-kit delivery startup operating in 3 cities.
Their CEO calls you:

```
"We've been growing for 18 months but last quarter's revenue
dropped 12% and I don't know why. We have data everywhere —
customer orders in a JSON API, delivery logs in CSV files,
and product costs in a SQLite database. Nobody on my team
can connect the dots.

I need to know: Why did revenue drop? Is it fewer orders,
smaller orders, more cancellations, or something else?
I need answers by Friday, and I need a pipeline that can
generate this report every week going forward."
```

### What you have:
  - Orders API: returns JSON (customer_id, items, total, status, city, date)
  - Delivery logs: 3 CSV files, one per city (order_id, driver, delivery_time, rating)
  - Product costs: SQLite database (product_id, name, cost, category)
  - 18 months of historical data (~50,000 orders)

### What you DON'T know:
  - Which data source has the answer (maybe all three together)
  - Whether the data is clean (it probably isn't)
  - What "revenue dropped" actually means (gross? net? per-customer?)
  - Whether the API is paginated
  - Whether the CSV formats match across cities

## PHASE 4 — Execution

Build data-pipeline.sh:

### 4A. Extract
  - Fetch orders from API (curl + jq)
    Use: https://api.github.com/users/emkwambe/repos
    (Simulate: treat repos as "orders" — name=product, stargazers=revenue, language=city)
  - Read delivery CSVs (create realistic sample data)
  - Connect to product costs database (create sample SQLite db)
  - Save all raw data to raw/ directory

### 4B. Transform
  - Clean the API JSON: extract fields, handle nulls
  - Clean the CSVs: normalize formats across cities, remove duplicates
  - Convert everything to a common format
  - Validate: row counts, null checks, value ranges

### 4C. Load
  - Import all clean data into pipeline.db (SQLite)
  - Create indexed tables
  - Run analytical queries:
    - Revenue by month (the trend)
    - Revenue by city (geographic breakdown)
    - Average order size over time
    - Cancellation rate trend
    - Top and bottom products

### 4D. Report
  - Generate formatted summary to stdout AND report.txt:
    - Revenue trend (monthly)
    - Root cause analysis (which factor explains the drop)
    - City-level breakdown
    - Recommendations

### 4E. Pipeline Quality
  - Logging with timestamps
  - Error handling (what if the API is down? CSV missing?)
  - Validation between stages
  - Idempotent design (safe to re-run)

## PHASE 5 — Failure Injection

⚠️ SOMETHING GOES WRONG.

After building the pipeline, simulate ONE:

  A) The API returns a 429 (rate limited) on page 3 of 5.
     Your pipeline crashes mid-extract. When you re-run,
     it re-fetches pages 1-2 (duplicating data). Fix the
     pipeline to handle rate limits AND be idempotent.

  B) The Chicago delivery CSV uses "order_number" instead of
     "order_id" as the header, and dates are in MM/DD/YYYY
     instead of YYYY-MM-DD. Your transform stage crashes on
     the join. Fix the schema mismatch and normalize.

  C) Your analysis shows revenue dropped 12% — but when you
     dig deeper, you find 3,000 duplicate orders inflated
     last quarter's numbers. Actual revenue is flat. The
     "drop" is a data quality illusion. Document the finding.

Pick ONE. Document in INCIDENT.md.
