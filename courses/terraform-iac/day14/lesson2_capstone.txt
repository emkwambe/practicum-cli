## PHASE 1 — Problem Context

### The Scenario:

NimbusMed is a telehealth startup with 15,000 active patients.
Their entire infrastructure runs in one AWS account, created
over 18 months of clicking through the AWS console:

  - 4 EC2 instances (nobody knows which does what)
  - 2 RDS databases (one might be unused)
  - Security groups with rules like "allow all from 0.0.0.0/0"
  - No staging environment — all testing happens on production
  - No infrastructure documentation
  - Last month: a developer accidentally terminated the wrong instance
    from the console. Recovery took 6 hours. Patient appointments
    were cancelled.

The CTO calls you:

```
"I need infrastructure I can trust. Something that rebuilds
itself if we break it. Something where every change is reviewed
before it goes live. I don't care what tool you use, I just
need to stop losing sleep over whether someone will delete
production again."
```

### What you know:
  - The app is a Node.js API + React frontend
  - PostgreSQL database with patient health records (HIPAA)
  - Redis for session caching
  - Everything runs in us-east-1
  - The team has never used IaC

### What you DON'T know:
  - Whether to import existing infra or rebuild from scratch
  - How to structure the Terraform project (mono-repo? modules?)
  - What the correct security group rules should be
  - Whether workspaces or directories for environments
  - How to handle the HIPAA requirements in IaC
  - How to train the team without disrupting patient services

## PHASE 4 — Execution

Build a Terraform project that provisions a complete stack.
Use the Docker provider (no cloud account needed):

### 4A. Project structure:
  nimbus-infra/
  ├── modules/
  │   ├── network/        # Docker networks
  │   ├── database/       # PostgreSQL container + volume
  │   ├── cache/          # Redis container
  │   └── web-server/     # App container
  ├── environments/
  │   ├── dev.tfvars
  │   └── prod.tfvars
  ├── main.tf             # calls modules
  ├── variables.tf
  ├── outputs.tf
  ├── providers.tf
  └── backend.tf

### 4B. Modules (at minimum):
  - network module: creates Docker networks (frontend, backend)
  - database module: PostgreSQL with named volume, health check
  - cache module: Redis container
  - web-server module: app container with configurable replicas

  Each module must have: variables.tf, main.tf, outputs.tf

### 4C. Environment configuration:
  - dev.tfvars: 1 web instance, small resources, debug logging
  - prod.tfvars: 2 web instances, larger resources, production logging

  Both environments from the SAME code.

### 4D. CI/CD integration:
  - .github/workflows/terraform.yml
    - On PR: fmt check → validate → plan → post plan as comment
    - On merge to main: apply with -auto-approve
  - .gitignore: state files, .terraform/, *.tfvars with secrets

### 4E. Operational outputs:
  - Web server URL
  - Database connection info (marked sensitive)
  - Network IDs

## PHASE 5 — Failure Injection

⚠️ SOMETHING GOES WRONG.

After building the stack, simulate ONE:

  A) A developer runs terraform apply in the prod workspace when
     they meant dev. The production database gets replaced with
     a dev-sized instance. Patient data volume is intact but
     the container changed. Document the incident and implement
     workspace safety controls.

  B) terraform plan shows "0 to add, 0 to change, 0 to destroy"
     but the web application is returning errors. Someone manually
     changed a Docker network setting outside of Terraform.
     Detect the drift, document it, and fix it through code.

  C) The state file gets corrupted (simulate by modifying
     terraform.tfstate manually). terraform plan shows it wants
     to destroy and recreate everything. How do you recover
     without destroying production infrastructure?

Pick ONE. Document in INCIDENT.md:
  1. What happened (timeline)
  2. Impact assessment
  3. Immediate action taken
  4. Root cause
  5. Permanent fix
  6. Process change to prevent recurrence
