## PHASE 1 — Problem Context

### The Scenario:

MedRelay is a healthcare communication platform that connects
doctors, nurses, and patients across 12 hospitals. They migrated
to Kubernetes 4 months ago. The team deployed services using
kubectl apply and raw YAML files. Nobody wrote documentation.

Yesterday at 2 PM:
  - The API service started returning 503 errors
  - The notification service stopped sending alerts
  - The database pod restarted 3 times
  - A nurse couldn't reach a doctor during a patient emergency

The CTO asks:

```
"I was told Kubernetes makes things reliable. Instead we had
our worst outage in 2 years. I need someone to stabilize this
cluster, set up proper monitoring, and make sure this never
happens again. We have 12 hospitals depending on us."
```

### What you know:
  - 5 microservices: API, web frontend, notification worker,
    auth service, PostgreSQL database
  - Running on a 3-node kind cluster (simulating their setup)
  - No health probes configured
  - No resource limits set
  - No HPA — all services run with replicas: 1
  - Secrets are in plain YAML files committed to Git
  - No Ingress — each service uses NodePort
  - No Helm — raw YAML files scattered in a directory

### What you DON'T know:
  - Why the API returned 503s (was it the API? the database? both?)
  - Whether the database lost data during restarts
  - How the notification service connects to the API
  - What resource consumption looks like under normal load
  - Whether the cluster can handle a node failure

## PHASE 4 — Execution

Build the stabilized cluster on kind:

### 4A. Cluster setup:
  kind create cluster --name medrelay --config kind-config.yaml
  (3 nodes: 1 control-plane, 2 workers)

### 4B. Namespace and RBAC:
  - Create namespace: medrelay-prod
  - Create a ServiceAccount for the CI/CD pipeline
  - Document RBAC approach (who can do what)

### 4C. Deployments (all 5 services):
  Each must have:
  - Deployment with >= 2 replicas (3 for API)
  - Resource requests AND limits
  - Liveness and readiness probes
  - Labels: app, tier, version

  Services:
  - api (3 replicas, port 3000)
  - web (2 replicas, port 80)
  - notification-worker (2 replicas, no port — queue consumer)
  - auth (2 replicas, port 4000)
  - postgres (StatefulSet, 1 replica, PVC for data)

### 4D. Networking:
  - ClusterIP services for internal communication
  - Ingress for external access (api.medrelay.local, app.medrelay.local)
  - NetworkPolicy: web→api, api→auth, api→postgres,
    notification→api. Nothing else.

### 4E. Configuration:
  - ConfigMap: DB_HOST, LOG_LEVEL, API_URL, QUEUE_URL
  - Secrets: DB_PASSWORD, JWT_SECRET, SMTP_PASSWORD
  - Secrets created via kubectl (not in YAML files)

### 4F. Storage:
  - PVC for PostgreSQL data (10Gi, ReadWriteOnce)
  - PDB on API (minAvailable: 2)

### 4G. Helm packaging:
  - Package the entire stack into a Helm chart
  - values-dev.yaml and values-prod.yaml
  - helm install medrelay ./chart -f values-prod.yaml

### 4H. Operational tooling:
  Create scripts/:
  - health-check.sh (verifies all pods, services, endpoints)
  - scale-api.sh (safely scales API with pre/post checks)

## PHASE 5 — Failure Injection

⚠️ SOMETHING GOES WRONG.

After building the stabilized cluster, simulate ONE:

  A) The API deployment is updated with a broken image tag.
     New pods enter CrashLoopBackOff. With maxUnavailable: 0
     the old pods should still serve traffic — verify this works.
     Then roll back. Document the entire incident.

  B) The PostgreSQL pod is killed (kubectl delete pod postgres-0).
     The StatefulSet recreates it. But the app throws "connection
     refused" for 30 seconds while PostgreSQL initializes.
     Investigate why readiness probes didn't prevent this.
     Fix the configuration.

  C) A developer accidentally applies a NetworkPolicy that blocks
     ALL traffic to the API pods. The web frontend returns 504s.
     Users can't access the platform. Diagnose, fix, and implement
     a review process for NetworkPolicy changes.

Pick ONE. Document in INCIDENT.md:
  1. Timeline (when did each thing happen)
  2. Detection (how was it discovered)
  3. Impact (which services, which users)
  4. Root cause
  5. Immediate fix
  6. Permanent prevention
  7. HIPAA implications

  [ ] Namespace isolation
  [ ] Labels and selectors consistent
