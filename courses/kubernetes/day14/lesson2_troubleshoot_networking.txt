# Lesson: Troubleshooting Networking — DNS, Services & Connectivity

## [WHEN] You need this when:
1. Pods can't reach other pods or services.
2. External traffic isn't reaching the cluster.
3. DNS resolution fails.
4. CKA Domain 5 (30%) specifically lists network troubleshooting.

## [INTENT] "Systematically diagnose and fix Kubernetes networking failures."

## [CONTEXT]
Networking failures are the most common CKA troubleshooting tasks.
They combine Service configuration, DNS resolution, NetworkPolicies,
CNI health, and Ingress routing. Each layer can fail independently.

## [ACTION] Network troubleshooting

### Layer-by-layer debugging:

  Layer 1: CNI (pod-to-pod basic connectivity)
  Layer 2: DNS (name resolution)
  Layer 3: Services (stable endpoints)
  Layer 4: NetworkPolicies (firewall rules)
  Layer 5: Ingress (external routing)

  Debug from bottom up — CNI before DNS before Services.

### Layer 1: CNI (pod-to-pod):
  # Can pods on the same node talk?
  kubectl exec pod-a -- ping pod-b-ip

  # Can pods on different nodes talk?
  kubectl exec pod-a-on-node1 -- ping pod-b-ip-on-node2

  # If cross-node fails:
  kubectl get pods -n kube-system | grep -E "calico|cilium|flannel"
  # CNI DaemonSet pods must be Running on all nodes.
  # If not: kubectl describe pod calico-node-xxx -n kube-system

  # Check CNI configuration:
  ls /etc/cni/net.d/        # on the affected node
  # Missing config = CNI not installed properly

### Layer 2: DNS:
  kubectl run dns-test --image=busybox:1.36 --rm -it -- nslookup kubernetes
  # Success? DNS works.
  # "can't resolve" ?

  # Is CoreDNS running?
  kubectl get pods -n kube-system -l k8s-app=kube-dns
  # If CrashLoopBackOff: kubectl logs coredns-xxx -n kube-system

  # Is the kube-dns Service healthy?
  kubectl get svc kube-dns -n kube-system
  kubectl get endpoints kube-dns -n kube-system

  # Is resolv.conf correct inside pods?
  kubectl exec pod -- cat /etc/resolv.conf
  # Should show: nameserver <kube-dns-ClusterIP>

### Layer 3: Services:
  # Does the Service have endpoints?
  kubectl get endpoints my-service
  # Empty → selector labels don't match pod labels

  # Compare:
  kubectl describe svc my-service    # Selector
  kubectl get pods --show-labels     # Pod labels

  # Port mapping correct?
  kubectl describe svc my-service
  # Port: 80          → what clients connect to
  # TargetPort: 3000  → what the container listens on
  # If the app listens on 8080 but targetPort says 3000 → connection refused

  # Test from inside the cluster:
  kubectl run curl-test --image=curlimages/curl --rm -it -- \
    curl -v http://my-service:80

### Layer 4: NetworkPolicies:
  kubectl get networkpolicies -n <namespace>
  # Any policies exist? If yes, they might be blocking traffic.

  # To test: temporarily delete the policy, check if traffic flows.
  # If it does: the policy is too restrictive.

  kubectl describe networkpolicy <name>
  # Check the Ingress/Egress rules — are the correct pods allowed?

  # Common mistake: egress policy without DNS (port 53) allowance
  # Symptom: "could not resolve host" even though CoreDNS is fine

### Layer 5: Ingress:
  kubectl get ingress
  kubectl describe ingress my-ingress

  # No ADDRESS → ingress controller not running
  kubectl get pods -n ingress-nginx

  # 404 → no rule matches the hostname/path
  # 502 → backend Service or pods aren't running
  # 503 → backend exists but can't serve traffic

  # Check the ingress controller logs:
  kubectl logs -n ingress-nginx deploy/ingress-nginx-controller

### CKA exam networking scenarios:

  Scenario: "Pod can't reach Service"
  Checklist:
  □ Service exists?
  □ Service has endpoints?
  □ Selector matches pod labels?
  □ TargetPort matches container port?
  □ NetworkPolicy blocking?
  □ DNS resolves the service name?
  □ Pod is Ready (readiness probe passing)?

  Scenario: "External traffic not reaching app"
  Checklist:
  □ Ingress controller running?
  □ Ingress resource configured?
  □ Backend Service exists with endpoints?
  □ Host/path matching correctly?
  □ TLS configured if HTTPS?

  Scenario: "Cross-namespace communication broken"
  Checklist:
  □ Using FQDN? (svc.namespace.svc.cluster.local)
  □ NetworkPolicy in target namespace allows source namespace?
  □ Source namespace labeled correctly for namespaceSelector?

### Useful debugging commands (CKA toolkit):
  kubectl run debug --image=busybox:1.36 --rm -it -- sh
  kubectl run curl --image=curlimages/curl --rm -it -- sh
  kubectl exec -it pod -- wget -qO- http://service:port
  kubectl port-forward svc/my-service 8080:80    # local tunnel

## [EXPECTED RESULT]
You can debug networking at every layer (CNI → DNS → Service →
NetworkPolicy → Ingress) and identify the exact failure point.

## Technician Tip:
CKA exam networking: always start with "does the Service have
endpoints?" (kubectl get endpoints). This one check eliminates
50% of networking problems. No endpoints = fix the label selector.
