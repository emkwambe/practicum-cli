# Lesson: ConfigMaps & Secrets — Externalizing Configuration

## [WHEN] You need this when:
1. Your app needs database URLs, API keys, feature flags.
2. Configuration differs between environments (dev vs prod).
3. Secrets must not be baked into container images.

## [INTENT] "Separate configuration from code using ConfigMaps and Secrets."

## [CONTEXT]
Hardcoding config in Docker images means rebuilding for every environment.
K8s separates config from images:
  ConfigMap: non-sensitive config (DB_HOST, LOG_LEVEL, FEATURE_FLAGS)
  Secret: sensitive config (DB_PASSWORD, API_KEY, TLS_CERT)

Both are injected into pods at runtime — the image stays the same.

## [ACTION] ConfigMaps and Secrets

### ConfigMap:
  apiVersion: v1
  kind: ConfigMap
  metadata:
    name: app-config
  data:
    DB_HOST: "postgres.default.svc.cluster.local"
    LOG_LEVEL: "info"
    FEATURE_NEW_UI: "true"

  # Use as environment variables:
  containers:
    - name: app
      envFrom:
        - configMapRef:
            name: app-config

  # Or mount as a file:
  volumes:
    - name: config
      configMap:
        name: app-config
  volumeMounts:
    - name: config
      mountPath: /etc/app/config

### Secrets:
  # Create from command line:
  kubectl create secret generic db-creds \
    --from-literal=DB_PASSWORD=supersecret \
    --from-literal=DB_USER=admin

  # Or from YAML (values must be base64-encoded):
  apiVersion: v1
  kind: Secret
  metadata:
    name: db-creds
  type: Opaque
  data:
    DB_PASSWORD: c3VwZXJzZWNyZXQ=    # echo -n "supersecret" | base64
    DB_USER: YWRtaW4=

  # Use in a pod:
  containers:
    - name: app
      env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-creds
              key: DB_PASSWORD

### ⚠️ Secrets are NOT encrypted by default:
  K8s Secrets are base64-encoded (NOT encrypted).
  Anyone with API access can read them.
  For real security:
    - Enable encryption at rest in etcd
    - Use external secret managers (Vault, AWS Secrets Manager)
    - Restrict RBAC access to secrets

### ConfigMap vs Secret decision:
  Would you be uncomfortable if this value appeared in logs?
    Yes → Secret
    No  → ConfigMap

### Updating config:
  ConfigMaps and Secrets can be updated without restarting pods
  IF mounted as files (the kubelet watches for changes).
  Environment variables require a pod restart to pick up changes.

## [EXPECTED RESULT]
You can externalize app config, inject it into pods, and understand
when to use ConfigMaps vs Secrets.

## Common Pain Point:
"My Secret value is wrong" → you forgot to base64-encode it in YAML.
Use kubectl create secret (no manual encoding needed) or
stringData: field (plain text, K8s encodes for you).
